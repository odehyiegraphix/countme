# AGENT.md

## Secure Geo-Location and Dynamic QR-Based Attendance Management System

### AI Coding Agent Instructions

---

# 1. Project Identity

You are the primary AI software engineering agent working on:

**Secure Geo-Location and Dynamic QR-Based Attendance Management System with Academic Performance Analytics**

The system is a responsive web application for tertiary institutions.

Its core purpose is to provide a secure, auditable attendance process using:

* Authentication
* Dynamic QR codes
* Geolocation verification
* Location accuracy validation
* Application-level device binding
* Database-level duplicate prevention
* Attendance attempt logging
* Controlled manual attendance
* Audit logging
* Rule-based anomaly detection
* Academic performance analytics
* Role-based stakeholder access

The system is NOT simply a QR attendance application.

The core technical contribution is:

> Dynamic QR verification + authenticated identity + geolocation + device binding + database integrity + auditability + academic performance analytics.

# 3. Development Philosophy

Follow these principles throughout development.

### 3.1 Security First

Attendance data is academic data.

Treat:

* student identity
* location
* attendance
* academic performance
* parent relationships
* audit records

as sensitive information.

Never expose information simply because it is technically accessible.

Always enforce authorization on the server.

---

### 3.2 Server Is the Authority

Never trust the browser for security decisions.

The client may provide:

* QR token
* coordinates
* device identifier
* session identifier
* student information

but the server must validate all important conditions.

Never rely on:

```text
frontend validation alone
```

for:

* authentication
* authorization
* QR validity
* attendance eligibility
* enrollment
* location acceptance
* duplicate prevention
* manual attendance permissions

---

### 3.3 Small, Testable Changes

Do not make large uncontrolled changes.

For every feature:

1. Understand the requirement.
2. Identify affected modules.
3. Implement.
4. Test.
5. Check for regressions.
6. Document important architectural decisions.

Prefer small commits and logically isolated changes.

---

### 3.4 Do Not Overengineer

This is a final-year project prototype.

Do not introduce:

* unnecessary microservices
* Kubernetes
* event-driven infrastructure
* machine-learning pipelines
* complex distributed systems
* unnecessary third-party services

unless explicitly required.

Prefer a modular monolith with a clean architecture.

# 9. Attendance Engine

The attendance engine is the most important component of the system.

Do not implement attendance as:

```text
scan QR -> mark present
```

Instead use:

```text
Authentication
      ↓
Session Validation
      ↓
QR Validation
      ↓
Enrollment Validation
      ↓
Time Validation
      ↓
Location Validation
      ↓
Location Accuracy
      ↓
Device Validation
      ↓
Duplicate Validation
      ↓
Create Attendance
```

Every stage must have a clear success/failure state.

---

# 10. Attendance Validation Rules

A student receives:

```text
VERIFIED
```

only when all required conditions pass.

Conceptually:

```text
Authenticated
AND
Active Session
AND
Valid QR
AND
Correct Course Enrollment
AND
Valid Time
AND
Location Within Radius
AND
Acceptable Location Accuracy
AND
Valid Device
AND
No Existing Attendance
```

If any required condition fails:

```text
Do not create verified attendance.
```

Instead:

```text
Create Attendance Attempt
+
Store Failure Reason
```

---

# 11. Attendance Attempt vs Attendance Record

These are different concepts.

## Attendance Attempt

Represents an attempt to submit attendance.

Possible results:

```text
VERIFIED
OUT_OF_RANGE
LOW_LOCATION_ACCURACY
INVALID_QR
EXPIRED_QR
NOT_ENROLLED
DUPLICATE
INVALID_SESSION
DEVICE_FLAGGED
REJECTED
```

---

## Attendance Record

Represents official attendance.

Possible methods:

```text
VERIFIED
MANUAL
```

Never overwrite the original failed attempt simply because a lecturer later approves a manual exception.

The history must remain auditable.

---

# 12. Dynamic QR Rules

QR codes must be:

* generated by the server
* short-lived
* session-specific
* cryptographically protected
* validated server-side

Conceptual payload:

```text
session_id
token_id
expiration
signature
```

Do not place unnecessary sensitive information in the QR.

---

## QR Validation

Reject:

* expired QR
* invalid signature
* unknown token
* inactive session
* invalid session
* malformed token
* replayed token where applicable

Do not trust:

```text
QR data supplied by frontend
```

until it has been validated by the backend.

---

# 13. QR Rotation

The active session should periodically receive a new valid token.

Conceptually:

```text
Session starts
      ↓
Token A generated
      ↓
Token A expires
      ↓
Token B generated
      ↓
Token B expires
      ↓
Token C generated
```

The exact interval should be configurable.

Do not hard-code the interval in multiple parts of the application.

Create a single configuration value.

---

# 14. Geolocation Rules

The browser provides:

```text
latitude
longitude
accuracy
```

The backend calculates distance from:

```text
Student location
```

to:

```text
Session location
```

Use the Haversine formula or equivalent.

---

## Acceptance

If:

```text
distance <= allowed_radius
```

and location accuracy is acceptable:

```text
continue validation
```

Otherwise:

```text
reject automated attendance
```

and record the attempt.

---

# 15. Out-of-Range Rule

Never silently convert an out-of-range attempt into attendance.

Example:

```text
Student
   ↓
Scan QR
   ↓
Location = 180m away
Allowed radius = 100m
   ↓
OUT_OF_RANGE
   ↓
Attendance NOT created
   ↓
Attempt logged
```

The lecturer may later use the manual exception workflow if there is a legitimate reason.

---

# 16. Location Accuracy

GPS coordinates are not perfect.

Do not assume:

```text
accuracy = 0
```

means perfect location.

Consider the reported accuracy when deciding whether automated verification is reliable.

The exact threshold should be configurable.

Do not scatter arbitrary values throughout the code.

---

# 17. Device Binding

Device binding is a supporting security signal.

It is NOT proof of physical identity.

Do not use:

```text
IMEI
MAC address
```

or other restricted hardware identifiers.

Use an application-level identifier permitted by the platform.

---

## Device Rules

When registering a device:

```text
Authenticated User
      ↓
Generate/obtain application-level identifier
      ↓
Store binding
```

During attendance:

```text
Current device
      ↓
Compare with registered binding
      ↓
Valid / Flagged
```

A device associated with many student accounts may generate an anomaly.

Do not automatically accuse the student of fraud.

---

# 18. Duplicate Prevention

Duplicate prevention must exist at two levels.

## Application Level

Check:

```text
Does attendance already exist?
```

## Database Level

Use a unique constraint:

```text
(session_id, student_id)
```

The database constraint is mandatory.

Never rely only on frontend or application-level checking.

Use transactions where necessary.

---

# 19. Manual Attendance

Manual attendance is an exception mechanism.

Valid examples:

* phone unavailable
* camera problem
* GPS failure
* institution-approved exception

Manual attendance must require:

```text
student
session
lecturer
reason
timestamp
method = MANUAL
```

---

## Manual Attendance Rules

Never allow:

```text
manual attendance without reason
```

Never hide manual attendance inside normal verified attendance.

The dashboard should distinguish:

```text
Verified Attendance
Manual Attendance
```

---

# 22. Anomaly Detection

Use simple rule-based anomaly detection.

Do not introduce machine learning unless explicitly required.

Examples:

### Device anomaly

```text
IF one device -> many student accounts
THEN flag
```

### Student location anomaly

```text
IF repeated out-of-range attempts
THEN flag
```

### Accuracy anomaly

```text
IF repeated poor-location readings
THEN flag
```

### Lecturer anomaly

```text
IF unusually high manual attendance rate
THEN flag
```

### QR anomaly

```text
IF repeated invalid/expired QR attempts
THEN flag
```

Alerts should be reviewable.

Do not automatically label users as dishonest.

# 27. Correlation Rules

Pearson correlation may be used where sufficient valid data exists.

Never present:

```text
correlation = causation
```

Use wording such as:

```text

```

Do not claim:

```text

```

```text

```

# 28. Privacy Rules

Only collect location when attendance verification requires it.

Do not implement continuous location tracking.

Users must only access information within their authorized scope.

Never expose:

* another student's exact location
* unrelated attendance
* unrelated performance
* private audit metadata

through an unauthorized endpoint.

# 29. API Security

Every protected API route must verify:

```text
Authentication
+
Authorization
+
Resource ownership/scope
```

Do not assume:

```text
if user is logged in -> user can access resource
```

For example:

```text
GET /students/123/attendance
```

must verify that the current user is allowed to access student 123.

# 30. Error Handling

Errors should be:

* clear
* safe
* actionable
* non-sensitive

Good:

```text

```

Bad:

```text

```

Never expose:

* stack traces
* SQL queries
* secrets
* internal tokens
* database credentials

to users.

# 52. Final Rule

When uncertain, prioritize in this order:

```text
1. Security
2. Data integrity
3. Correctness
4. Authorization
5. Auditability
6. User experience
```
